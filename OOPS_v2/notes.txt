Method overriding : 
-Compiler → reference type → determines WHAT methods you are allowed to call
-Runtime/JVM → actual object → determines WHICH overridden implementation executes
class Animal {
    void sound() {
        System.out.println("Animal");
    }
}

class Dog extends Animal {
    @Override
    void sound() {
        System.out.println("Dog");
    }

    void bite() {
        System.out.println("Bite");
    }
}
Animal animal = new Dog();

animal.sound(); // ✅ Dog
animal.bite();  // ❌ Compile-time error

animal.sound()

Compiler:
Animal has sound()? → YES ✅

Runtime:
Actual object = Dog
Dog overrides sound()? → YES
Execute Dog.sound()


animal.bite()

Compiler:
Animal has bite()? → NO ❌

STOP.
Runtime is never reached.
But the Dog object really DOES contain bite()
Absolutely. The object itself is still a complete Dog object.

--You can prove that by downcasting:
Animal animal = new Dog();
Dog dog = (Dog) animal;
dog.bite();



Why would this generally be worse:

class EmployeeService extends EmployeeRepository {
}

than:

class EmployeeService {


    private EmployeeRepository employeeRepository;
}



Question : 
class EmployeeService extends EmployeeRepository {
}

This means:

EmployeeService IS-A EmployeeRepository

Ask yourself: Is an employee service actually a repository? -> No.

A service uses a repository.

So the correct relationship is:

class EmployeeService {
    private EmployeeRepository employeeRepository;
}

This means:
EmployeeService HAS-A EmployeeRepository -That is composition.
The bigger reason is coupling. If EmployeeService extends EmployeeRepository, your service becomes tightly coupled to that repository implementation. It also inherits repository methods whether it needs them or not.

With composition:
class EmployeeService {
    private final EmployeeRepository repository;
    public EmployeeService(EmployeeRepository repository) {
        this.repository = repository;
    }
}

you can easily replace the repository:

EmployeeRepository repo = new MongoEmployeeRepository();

or later:

EmployeeRepository repo = new JpaEmployeeRepository();

without changing the EmployeeService design.

A simple rule to remember:

Inheritance → IS-A
Composition → HAS-A

So before using extends, ask:
"Is this class genuinely a type of the parent class?"

For Dog extends Animal → yes.
For EmployeeService extends EmployeeRepository → no.
That is why in Spring you typically see:

@Service
class EmployeeService {
    private final EmployeeRepository repository;
}

instead of extending repositories.
And this is exactly what people mean when they say:
Favor composition over inheritance.



Abstract Classes Vs Interfaces 
An abstract class says:
- “These classes are closely related and can share some common code.”
abstract class Vehicle {
    void start() {
        System.out.println("Vehicle starts");
    }

    abstract void makeSound();
}
class Bike extends Vehicle {
    void makeSound() {
        System.out.println("Bike sound");
    }
}

An interface says:
- “Any class that agrees to this must provide these abilities.”
-  An interface is more like a contract:
interface Flyable {
    void fly();
}
class Bird implements Flyable {
    public void fly() {
        System.out.println("Bird flies");
    }
}

class Airplane implements Flyable {
    public void fly() {
        System.out.println("Airplane flies");
    }
}

Overloading vs Overriding

Overloading
→ reference/argument type matters
→ decided at compile time

Overriding
→ actual object matters
→ decided at runtime

| Overloading                                 | Overriding                 |
| ------------------------------------------- | -------------------------- |
| Same class usually                          | Parent-child relationship  |
| Same method name                            | Same method name           |
| Different parameters                        | Same parameters            |
| Compile-time decision                       | Runtime decision           |
| Return type may differ if signature permits | Return type same/covariant |
| Inheritance not required                    | Inheritance required       |
| Static binding                              | Dynamic binding            |


#A covariant return type just means:
When overriding a method, the child class can return a more specific type than the parent method.
covariant return type is not about what fields get filled. It's about preserving the type contract while overriding.
For example:

class Animal {
    String name;
}

class Dog extends Animal {
    String breed;
}

Parent method:

Animal getAnimal() {
    return new Animal();
}

Child override:

@Override
Dog getAnimal() {
    return new Dog();
}


#static methods overriding 
Static methods belong to the class, not the object.

Example:
class Animal {

    static void sound() {
        System.out.println("Animal");
    }
}
class Dog extends Animal {

    static void sound() {
        System.out.println("Dog");
    }
}

Then:
Animal animal = new Dog();
animal.sound();

prints:
Animal

This is called method hiding, not overriding.
Because static method resolution happens using the reference/class type.
Rule: 
private → cannot override
static  → hidden, not overridden
final   → cannot override


class Animal {

    void eat(Animal a) {
        System.out.println("Animal eat");
    }
}

class Dog extends Animal {

    void eat(Dog d) {
        System.out.println("Dog eat");
    }
}

Animal a = new Dog();
Dog d = new Dog();

a.eat(d);
Overloading → compiler decides using reference types.
Overriding → runtime decides using the actual object.
